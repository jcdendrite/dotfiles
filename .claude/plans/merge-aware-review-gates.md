# Merge-aware review gates

## Context

Make the commit-time review gates correct in every in-progress git state —
merge, rebase, cherry-pick, and revert — so that a commit concluding one of
those operations is gated on the content its author actually wrote, and is
gated at all — with one deliberate exception: `git rebase --continue` is
carved out of the two review-marker gates specifically (`require-code-review.sh`,
`require-skill-review.sh`), while gaining coverage from every other gate this
plan fixes. See the rebase carve-out below for why.

Three defects surfaced together, and they are the same bug seen from two
sides. A session syncing a feature branch with `git merge origin/main` hit
the first: `require-code-review.sh:108` hashes `git diff --cached`, which
during a merge means index-versus-pre-merge-`HEAD`, so every file the other
parent brought in reads as unreviewed staged content. That session was told
to obtain a fresh review of twelve `SKILL.md` files and dozens of other files
already reviewed on their own PRs. `require-skill-review.sh:221`
(`plugins/skill-management/hooks/`), `_lib_active_plan_files` (`_lib.sh:392`,
which promotes upstream's already-merged plan files to "active plans"), and
`_lib_staged_length_gate` (`_lib.sh:1031`, which charges upstream's line
growth to the merger) all fail the same way. A repo-wide grep for
`MERGE_HEAD|CHERRY_PICK_HEAD|REBASE_HEAD|MERGE_MSG` across every `.sh` and
`.py` returns zero files: nothing in the gate system knows an in-progress
operation exists.

The second defect is the same gap inverted. `_lib_extract_git_subcmd`
(`_lib.sh:621`) returns the first non-flag word after `git`, so
`git merge --continue` extracts `merge`, never `commit`. Verified by running
the matchers directly: `git merge --continue`, `git rebase --continue`,
`git cherry-pick --continue`, `git revert --continue`, `git merge origin/main`,
`git rebase origin/main`, and `git cherry-pick <sha>` all exit no-opinion from
six gates — `require-code-review.sh`, `require-skill-review.sh`,
`check-skill-length.sh`, `check-claude-md-length.sh`, `deny-pii-in-commits.sh`,
and `guard-settings-session-keys.sh`. `deny-private-project-refs.sh` shares
the identical gap by the same architectural cause — it calls
`_lib_extract_git_subcmd` directly (`:310`), the same primitive
`deny-pii-in-commits.sh` calls — bringing the total to **seven**; this
inclusion is inferred from the shared call site, not independently executed
against the same seven commands. The same merge is therefore either
over-gated or entirely ungated depending on which command concludes it, and
rebase — this repo's default sync strategy per `git-feature-branch-sync` —
is the ungated arm for all seven. This plan closes that gap for `merge`,
`cherry-pick`, and `revert` `--continue` across all seven gates, and for
`rebase --continue` across five of the seven — `deny-pii-in-commits.sh`,
`deny-private-project-refs.sh`, `check-skill-length.sh`,
`check-claude-md-length.sh`, and `guard-settings-session-keys.sh`.
`git rebase --continue` keeps skipping the remaining one, `require-code-review.sh`
(and its plugin-side skill-review counterpart), by deliberate carve-out — see
below — not by oversight.

The third is adjacent and lands in a file the second already touches.
`require-skill-review.sh:83` matches commits with a plain
`grep -qE '(^|&&?|;|\|\|?)\s*git\s+commit(\s|$)'` regex rather than the
fragment-aware `_lib_command_invokes_git_subcmd` its sibling uses. Confirmed
live with a `SKILL.md` staged and no marker: `git -c core.editor=true commit`
returns ALLOW from the skill-review gate and DENY from the code-review gate,
so a `SKILL.md` change can reach a commit without `/skill-review` ever running.

Why now: merge is a documented, mandated path, not an accident.
`git-feature-branch-sync/SKILL.md` names four merge-required conditions —
another active committer, a stacked child branch, SHA-anchored review in
flight, and merge-only project policy — under which it instructs
`git merge --no-ff origin/main`. The state has simply never been exercised
here: zero merge commits in 701, and the GitHub repo is squash-merge-only
(`mergeCommitAllowed:false`, `rebaseMergeAllowed:false`). No commit in the
repo's history raises merge-commit gate handling; `git log -i --grep="merge-aware"`
returns zero hits. This is an unhandled state, not a recorded tradeoff.

Intended outcome: one shared in-progress-state helper, used by every gate that
derives a trigger or a hash from `git diff --cached`, so that each gate reviews
exactly the content novel to the commit being made; commit-shape detection that
recognizes the `--continue` family across all six gates, except for a deliberate
narrower recognition on the two review-marker gates that excludes `rebase --continue`;
and `require-skill-review.sh` routed onto the shared fragment-aware matcher. Marker
write, read, and status paths must move together, or a marker written under one
recipe can never match the gate reading it under another.

## Approach

Two new primitives in `claude/.claude/hooks/_lib.sh`, then a call-site sweep that moves every marker's write, read, and status path together. A gate stops charging a merger for content it can prove is already committed — and proves it, rather than trusting a file in the gitdir.

**`_lib_gate_diff_base REPO_ROOT`** prints the tree-ish a gate should diff against *instead of* the index's default base. During a trusted in-progress operation it prints the OID of the tree git's own automatic apply would have produced, so `git diff --cached "$BASE"` is exactly the content the human authored on top of that — conflict resolutions plus hand edits, with nothing the other side brought in. Everywhere else it prints **nothing**, and the call site issues `git diff --cached` with no base argument, which is byte-for-byte the command running today. That empty-string convention is load-bearing twice over: it keeps the marker preimage unchanged outside an in-progress state (so no marker on disk invalidates when this ships), and it avoids `git diff --cached HEAD`, which fails on an unborn branch where today's `git diff --cached` succeeds. Call sites that need a rev prefix rather than a diff base — `git show "<rev>:<path>"` in `_lib_staged_length_gate`, the explicit `HEAD` in `_lib_active_plan_files` — use `"${BASE:-HEAD}"`.

**`_lib_command_concludes_commit COMMAND`** is a tri-state sibling of `_lib_command_invokes_git_subcmd`, true for `git commit` and for `git <merge|rebase|cherry-pick|revert> --continue`.

**`_lib_command_concludes_marker_gated_commit COMMAND`** is a second tri-state predicate, narrower by exactly one case: true for the same set minus `git rebase --continue`. Both delegate to one private matcher parameterized on the shape set, so the rebase-membership decision is written once, not duplicated across two independent regexes — see the rebase carve-out below for why the narrower set exists and M-9 for the mechanics.

One gate-adjacent defect is found and recorded but **not fixed here**: the round-3 architect-consult gate is disarmed for the whole duration of a rebase, because `_lib_reviewer_round_state_key` keys on the branch name and rebase runs on a detached HEAD (row 27). This plan does not widen that window — `require-code-review.sh` never fires on `git rebase --continue` (the carve-out below), so no new `/code-review` or reviewer fan-out is compelled mid-rebase where none was compelled before. Phase 2 touches the adjacent `_lib_reviewer_round_state_value` (its diff-hash half only) without affecting the key's branch-half disarm. Accepted as residual 18, at a smaller scope than an earlier draft of this plan gave it.

### The rebase carve-out: `git rebase --continue` skips the two review-marker gates

**Not yet wired.** `_lib_command_concludes_commit` and `_lib_command_concludes_marker_gated_commit` exist in `_lib.sh` but have zero production callers as of Phase 1 — no hook invokes either yet, so `git rebase --continue` (and the `merge`/`cherry-pick`/`revert --continue` forms) still bypasses all seven gates identically to pre-plan behavior. The "five gates stay armed" property this section describes is a Phase 3 target, wired at the call sites listed there, not current behavior.

The engineer's explicit instruction: do not gate `git rebase --continue` through `require-code-review.sh` or `require-skill-review.sh`. Rationale, verified rather than assumed. The commits a rebase replays already passed `require-code-review.sh` once, at their own original commit time — re-running a full `/code-review` (with reviewer fan-out) at every conflicted step of a rebase reviews content that is, for the most part, already-reviewed, at a cost this plan's own trust predicate cannot reduce: `REBASE_HEAD` reaches neither admissible anchor in the ordinary case (line 102), so the marker gates would fall back to a full HEAD-relative diff every time, not a novel-content one. The premise that the rebase's *start* is itself gated does not hold — no hook matches the initiating `git rebase <upstream>` command (residual 2), so "gated" there can only mean "the replayed commits were reviewed originally," which covers the replay but not fresh conflict-resolution content authored mid-rebase. That resolution content is real and unreviewed by anything mechanical once this carve-out lands; it is caught, if at all, by whichever of the five non-marker gates still fire (the content scanners, the length gates, `guard-settings-session-keys.sh`) or by a human or reviewer-agent pass later, never by an automated code-review pass at commit time. `claude-skills/skills/ready-for-review/SKILL.md`'s cumulative-diff `/code-review` pass does not backstop this uniformly: it is a reviewer-agent read, not a mechanical scanner (no equivalent to `deny-pii-in-commits.sh`'s credential-pattern scan or `deny-private-project-refs.sh`'s structural detectors), and it is skipped outright on a `cumulative-review` marker cache hit (`ready-for-review/SKILL.md`'s step 3). The carve-out is accepted anyway, on cost/benefit: a mid-rebase `/code-review` demand at every conflicted step is real, recurring friction against content that is mostly already reviewed, and the five gates that stay armed (see below) are the ones with no review cost — a mechanical scanner or line-count check, not a reviewer dispatch.

The carve-out is **narrower than a blanket exemption**. Only `require-code-review.sh` and `require-skill-review.sh` — the two gates that demand a review and write a marker — are exempted. The five gates whose deny recourse is mechanical, not a review ("remove the value and re-stage," "shorten the file," "unstage the key") stay armed on `rebase --continue` via the broad `_lib_command_concludes_commit`: `deny-pii-in-commits.sh`, `deny-private-project-refs.sh`, `check-skill-length.sh`, `check-claude-md-length.sh`, and `guard-settings-session-keys.sh`. In particular, the two content scanners are **not** carved out — this plan's own three-buckets rule states narrowing a scanner's reach is a security regression, and that rule's reasoning is about accidental leakage, not about an adversary's cheapest bypass route; an accidental secret introduced during rebase conflict resolution does not route around whichever gate is armed, it walks into it. Exempting the scanners too would reopen exactly the always-on-scanner gap this plan closes for every other `--continue` form.

This creates a real, if narrow, incentive gradient: after this plan, `git merge --continue` is review-gated and `git rebase --continue` is not, for the same class of novel content. That gradient happens to point toward this repo's already-prescribed default (`git-feature-branch-sync/SKILL.md` prescribes rebase), so it does not create new pressure toward a worse workflow — but that alignment is coincidental to this decision, not a designed property of it, and the Phase 5 design-decisions entry records that the reasoning must be re-run if this repo's prescribed default sync strategy ever changes to favor merge.

### The trust predicate: excluded content must already be committed somewhere trusted

A gate may exclude a parent's content only when it can prove that content already passed a review gate. Presence of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, or a `rebase-merge/` directory proves nothing — all four are plain files any ungated `git update-ref` or `printf` can write, and a fabricated one pointing at a `commit-tree`-built commit that already contains a payload would make that payload vanish from the authorization hash while a real, matching marker is written over the narrowed diff. So the OID a state names is checked before its content is trusted:

```
git merge-base --is-ancestor "$oid" "origin/$(_lib_resolve_default_branch "$repo_root")"   # reviewed upstream
git merge-base --is-ancestor "$oid" HEAD                                     # already committed here
```

Either succeeding makes the state trusted. Neither succeeding — including a garbage or dangling OID, where `--is-ancestor` errors rather than returning 1 — falls back to the empty base.

The two anchors are not chosen for unforgeability; neither is unforgeable, and the plan does not claim otherwise. They are chosen because they pass the **anchor-admissibility test** (row 23), which has two legs rather than one: **soundness** — when honestly satisfied, does reaching the anchor mean the content already passed review? — and **non-dominance** — is *dishonestly* satisfying it (forging it for content that never passed review) cheaper than a bypass this plan already accepts as a residual and does nothing to close? The second leg's baseline is deliberately not "cheaper than passing the gate": G-6's ungated local plumbing (`commit-tree`, `hash-object`, `mktree`, `update-ref`, `git branch`, and — corrected below — several more) means an agent can already reach a commit with **zero gate firing at all**, at zero forgery cost, so "cheaper than the gate" was never the right ceiling to test against.

`HEAD` passes both legs. Soundness holds because content becomes reachable from `HEAD` only by being committed here, and committing here runs this gate. Non-dominance holds trivially: forging `HEAD` onto payload content *is* landing the payload — there is no cheaper dishonest route to the same outcome, because that route already is the outcome (row 14, with the same G-6-bypass caveat noted there).

`origin/<default>` passes on soundness by workflow, not by any claim that forging it is blocked: this repo is squash-merge-only, and the one path that legitimately moves that ref is the engineer's own PR merge, which `block-gh-pr-merge.sh` bars every agent from performing (row 24). It passes non-dominance because **residual 1 already exists and is cheaper**: `git commit-tree` a payload, `git branch payload <oid>`, `git merge payload` — a clean merge creates its commit inside the initiating command with no separate `git commit` for any gate to see (G-3), so this reaches a commit with no forgery, no refspec trickery, and no marker at all. Forging `refs/remotes/origin/<default>` to smuggle the same payload through a *conflicted* merge is strictly more work for a strictly worse outcome — it still requires engineering a conflict, resolving it, and it leaves a marker behind — so no agent takes it in preference to the bypass this plan already leaves open. Row 24 details what forging this anchor now costs, corrected to withdraw two claims that do not hold; row 28 covers the direct-push path; residual 19 records why that path is left open regardless.

Anything an agent can conjure locally and leave standing is checked against this same pair of legs, not against a shrinking list of named primitives — see the corrected G-6.

State detection uses one `git rev-parse --absolute-git-dir` plus file tests on the per-worktree markers, in this precedence order — rebase first, so a conflicted `rebase -i` that also writes `CHERRY_PICK_HEAD` resolves as rebase:

| State | Detected by | OID checked | Reference tree when trusted |
|---|---|---|---|
| rebase | `rebase-merge/` or `rebase-apply/` dir | `REBASE_HEAD` | `merge-tree --write-tree --merge-base=REBASE_HEAD^ HEAD REBASE_HEAD` |
| merge | `MERGE_HEAD` (single line) | `MERGE_HEAD` | `merge-tree --write-tree HEAD MERGE_HEAD` |
| cherry-pick | `CHERRY_PICK_HEAD` | `CHERRY_PICK_HEAD` | `merge-tree --write-tree --merge-base=CHERRY_PICK_HEAD^ HEAD CHERRY_PICK_HEAD` |
| revert | `REVERT_HEAD` | `REVERT_HEAD` | `merge-tree --write-tree --merge-base=REVERT_HEAD HEAD REVERT_HEAD^` |

The predicate is uniform, but its per-state hit rate is not, and the plan states that plainly rather than implying four equally-served arms. `git merge origin/<default>` — the case `git-feature-branch-sync/SKILL.md:47` prescribes and the case that motivated this plan — passes on the first anchor. A genuine revert passes on the second, since `REVERT_HEAD` is an ancestor of `HEAD` by construction. A cherry-pick passes only when its source is already upstream (backporting a landed hotfix); cherry-picking an unmerged commit fails both anchors and over-gates, which is the right answer — that content genuinely has not been reviewed on this branch. A rebase fails both anchors in the ordinary case, because `REBASE_HEAD` is the pre-rebase commit being replayed and mid-rebase `HEAD` is the new base plus already-replayed commits. Rebase therefore keeps today's HEAD-relative over-gating wherever it is still gated; what rebase gains from this plan is being **gated by the five non-marker gates**, via the broad `_lib_command_concludes_commit` — `require-code-review.sh` and `require-skill-review.sh` are deliberately excluded from `rebase --continue` by the rebase carve-out above. Out of scope #14 records the cost, names the two anchors that were proposed and declined, and states the admissibility test as the reopening criterion.

The `--rebase-merges` hazard — `REBASE_HEAD^` silently resolving to parent 1 of a replayed merge commit, producing a valid-looking tree computed against the wrong base — is closed by the same predicate rather than by a second mechanism: a replayed merge commit reaches neither anchor, so the rebase row never runs for it.

Validation of `merge-tree`'s output is uniform and version-agnostic: take stdout's first line via bash parameter expansion (`line="${out%%$'\n'*}"`, the idiom `_lib_extract_git_subcmd` already uses at `_lib.sh:621-626`, not a `head -1` fork) and require `git rev-parse --verify --quiet "<line>^{tree}"` to succeed. Anything else — git older than 2.38 rejecting `--write-tree`, a git accepting `--write-tree` but rejecting `--merge-base=`, an octopus `MERGE_HEAD`, a root commit with no `^` — yields the empty base. Every fallback over-scopes rather than under-scopes: it demands more review, never less. No version literal appears anywhere in the code.

### Contract: tri-state, modeled on `_lib_command_invokes_git_subcmd`, not on `_lib_active_plan_hash`

`_lib_active_plan_hash`'s three-outcome contract (`_lib.sh:425-439`) is the wrong model and the plan no longer cites it. Its exit-1 branch exists because that function has no safe default — empty stdout there means "disarmed," so a transient failure read as empty is fail-*open*. `_lib_gate_diff_base` has a safe default: the empty base is today's behavior and is strictly the conservative direction. The right precedent is `_lib_command_invokes_git_subcmd`'s tri-state, whose call-site contract (`_lib.sh:795-801`) already establishes status 2 as "undetermined" in this file:

- **exit 0, stdout = a tree OID** — an in-progress state was detected, its OID reached a trusted anchor, and the reference tree was computed.
- **exit 1, stdout empty** — no in-progress state, or one whose OID reached no anchor, or a topology or git version this design computes no base for. The empty base is the correct answer, not a degradation.
- **exit 2, stdout empty** — undetermined: a `_lib_capped` call inside the detection or computation path timed out, was killed, or its binary was missing.

**"exit 2 ⇒ empty stdout" is the contract's safety property, not a nicety.** Every caller uses stdout unconditionally regardless of exit status, so a partial or candidate OID escaping on the kill path would be consumed as a real base and would narrow an authorization hash on nobody's authority. Phase 1 assertion 8 injects that fault directly rather than inferring it from the version-fallback cases.

**No caller changes its allow/deny decision on status 2.** Denying on 2 would be wrong here in a way it is not wrong for `_lib_command_invokes_git_subcmd`: `merge-tree`'s whole-tree rename detection scales with whatever repo the contributor has open, not with claude-config, so on a large enough repo the 5s cap fires on a legitimate merge and denying would leave no recourse but the `bash -c` bypass this repo already treats as a residual. Status 2 is not left mute, though. A status-2 fallback and a genuine no-state result produce the same empty base and therefore the same over-gating deny, so `require-code-review.sh` and `require-skill-review.sh` name the undetermined base in the deny message they were already going to emit — otherwise the contributor reads that deny as this plan not working (residual 20). No log file, counter, or telemetry surface is added for it; the deny string is the one place the contributor is already reading. The status is not vestigial in the suite either: it is the only thing that lets a fallback test assert *which* fallback fired, which is exactly what the `--merge-base=`-rejected stub case and the per-call-site fallback matrix in Verification need. A test that cannot tell "fell back because the flag was rejected" from "fell back because no state was detected" asserts nothing.

`_lib_git_inprogress_state REPO_ROOT` carries the same three outcomes, printing the state name on 0.

**`REPO_ROOT` is mandatory on both.** The earlier draft would have let it be empty and defaulted to ambient cwd, generalizing `_lib_staged_length_gate`'s existing gap — that function resolves no root at all and calls bare `git` throughout (`_lib.sh:1024`, `:1030-1031`, `:1037`). Both of its callers already run `_lib_parse_tool_input_or_deny` (`check-skill-length.sh:57`), so the payload's `.cwd` is available to them exactly as it is to `require-code-review.sh:80-83`. The fix is three lines in each caller plus a root parameter on `_lib_staged_length_gate`, not a permanent dual-mode branch in a shared primitive that every future caller must reason about. `docs/hooks.md`'s "Which tree a marker describes" section makes root identity load-bearing; a hook whose ambient cwd diverges from its payload's `.cwd` would silently compute against the wrong tree, which is a different failure class from "conservatively over-scopes."

### Which gates get the new base — three buckets, not two

- **Authorize or measure growth** → novel-content base. Marker preimages (`require-code-review.sh`, `require-skill-review.sh`, `marker.sh`'s write and status arms), `_lib_active_plan_files`, `_lib_staged_length_gate`, `_lib_reviewer_round_state_value`. Charging a merger for upstream's content is the defect.
- **Scan for forbidden content** → no base change ever. `deny-pii-in-commits.sh`, `deny-private-project-refs.sh` gain `--continue` detection only; narrowing a scanner's input is a security regression.
- **Compare against a named branch** → unaffected by either base. `guard-settings-session-keys.sh` diffs staged `settings.json` against `main:claude/.claude/settings.json` (`:61-80`), using a bare `git diff --cached --name-only` at `:71` only as a staged-file trigger; `require-plugin-version-bump.sh:137` and `require-npm-version-bump.sh:174` already pass an explicit merge-base argument. These gates get `--continue` detection and nothing else.

**The first bucket's members do not fail identically.** Three of them — the marker preimages, `_lib_active_plan_files`, and `_lib_reviewer_round_state_value` — hash or enumerate an *absolute* diff against the base, so every in-progress state where the base is wrong drags the other parent's whole contribution into the result. `_lib_staged_length_gate` does not: it compares `git show ":$f"` against `git show "${BASE:-HEAD}:$f"` and fails only when `new > limit && new > old` (`_lib.sh:1029-1037`), a *delta* against whatever the base names. Mid-rebase, with the anchor unresolved and the base empty, `old` is the file at mid-rebase `HEAD` — the new base plus the replays so far — which is exactly the right pre-commit baseline for the commit being replayed, so this consumer has no rebase-specific over-count whether or not the rebase anchor resolves (row 26). Its only over-count is the mid-merge one, where `old` would otherwise be the pre-merge feature tip and upstream's growth gets charged to the merger; that is the case this plan fixes. Stating this keeps a reader from concluding that all four consumers break in all four states.

### One computation per process

`_lib_gate_diff_base` is resolved **once per hook-script invocation and once per `marker.sh` subcommand arm**, stored in a local, and threaded through every consumer in that process. This is an implementation requirement, not an emergent property of "one-token change": `require-code-review.sh` has two consuming sites (`:93`, `:108`), `require-skill-review.sh` has four (`:108-109`, `:116`, `:221`), `marker.sh status` computes the code-review and skill-review values back to back (`:525-534`), and `_lib_staged_length_gate` calls `git show "HEAD:$f"` **inside a `while IFS= read -r f` loop** (`_lib.sh:1030-1031`) — a literal substitution there would spawn state detection and a full `merge-tree --write-tree` once per staged file for a value identical on every iteration. The base is hoisted above that loop. The resolved *status* is stored alongside the base in the two commit gates, since their deny message reports it.

`_lib_staged_diff_hash REPO_ROOT BASE [pathspec...]` makes the threading structural rather than conventional: it takes an already-resolved base, so a call site physically cannot recompute one. It collapses the six inline copies of the staged-diff-hash recipe plus `_lib_reviewer_round_state_value`'s seventh (`_lib.sh:2286`). This is not deferrable cleanup — `marker.sh`'s write arm and the reading hook must compute a byte-identical preimage, and adding a base-resolution step to seven independent copies is seven chances to diverge into a marker that can never match. `_lib_active_plan_hash` and `_lib_cumulative_diff_hash` are the precedent: each already has exactly one implementation called from both sides.

### The plugin arm

`plugins/skill-management/hooks/require-skill-review.sh` cannot source across the plugin boundary (`plugins/skill-management/hooks/_lib.sh:16` states this outright), so its half is duplicated into that trimmed lib and pinned by behavioral-parity tests in the established `test_plugin_lib_sh_*_matches_stowed_lib_sh` shape (`test_require_skill_review.py:849-909`), not by whole-file byte comparison — that file's own docstring at `:888-893` explains why byte identity is the wrong invariant here.

The parity shape does not transfer unmodified. It is a fixed-input, single-call, byte-for-byte comparison: correct for the pure string processors, but against a repo that is not mid-operation it exercises only the empty-base branch of `_lib_git_inprogress_state`, `_lib_gate_diff_base`, and `_lib_staged_diff_hash` — the one branch two copies are least likely to diverge on, since it is the behavior neither copy is changing. Those three get **differential tests over Phase 1's real conflicted-state fixtures, run against both lib copies**, and those tests are standing, not introduction-time: they fail whenever the two copies disagree on any fixture, so a future fix to one side is structurally forced onto the other. This is the mitigation for the genuine increase in duplication risk — the skill-review marker's write side (`marker.sh`, stow copy) and read side (`require-skill-review.sh`, plugin copy) become two maintained implementations of a state machine, where before they were two copies of a one-liner.

**Root problem:** every commit-time review gate derives its trigger and its authorization hash from `git diff --cached`, which mid-operation compares the index against a tree that is not the commit's content baseline — so a merge is over-gated on content someone else already reviewed, and a `--continue` commit is not gated at all.

**Givens**

- **G-2** — A plugin cannot source the stowed `_lib.sh`; shared logic must be duplicated into each plugin's trimmed copy (`plugins/skill-management/hooks/_lib.sh:9-16`). The plugin packaging boundary is Claude Code's, not this repo's.
- **G-3** — PreToolUse gates see Bash *tool calls* only. A clean merge, rebase, or cherry-pick creates its commit inside the initiating command with no separate commit call, so it is invisible to every gate and stays so. The same property moves `HEAD` forward at each successfully replayed commit of a rebase with no Bash call of the agent's own.
- **G-4** — `git` offers no index-time combined diff. `man git-diff:73` ("If A is a merge commit, then `git diff A A^@`, `git diff A^!` and `git show A` all give the same combined diff") makes every combined form require the merge commit to already exist, and `man git-diff-index`'s synopsis carries no `-c`/`--cc`. A computed reference tree is the floor, not a choice. `[engineer-verified]`

**Mechanisms**

- **M-1 `git merge-tree --write-tree` as the reference tree.** The heaviest mechanism here: it writes loose objects into the ODB from inside a PreToolUse hook. It runs under `_lib_capped`, like every git call this plan adds. Two lighter primitives were checked and both fail. *Combined diff at index time* is the lightest and needs no computation at all, but G-4 rules it out — no index-time form exists. *Path intersection* — paths(`diff --cached HEAD`) ∩ paths(`diff --cached MERGE_HEAD`) — needs no object writes and no version floor, but is path-granular: a file both branches touched in different hunks, auto-merged cleanly, still hashes upstream's hunks. In this repo `_lib.sh` is exactly that file, so the failure case is the common one. `merge-tree` is already this repo's own primitive at `check-branch-divergence.sh:98` and `branch-divergence-status.sh:64`, and per `man git-merge-tree` it touches neither working tree nor index — but that precedent validates the primitive's tree-and-index safety only, not its latency posture: both cited calls are unwrapped, with only the `git fetch` preceding them time-bounded by a bare `timeout 2` (`check-branch-divergence.sh:80-86`), so this plan's are the first `_lib_capped`-guarded uses of it here (residual 21). - **Documented-behavior assertions**, so a future contributor reads these as intentional rather than as gaps: a clean `git cherry-pick <sha>` and a clean `git revert <sha>` reach no gate (residual 1), `require-plugin-version-bump.sh`/`require-npm-version-bump.sh` still allow `git -c core.editor=true commit` (residual 7), and `git rebase --continue` reaches neither `require-code-review.sh` nor `require-skill-review.sh` (the rebase carve-out — this is the same negative assertion the split bullet above states, cross-referenced here so a reader scanning this documented-behavior list doesn't need to also know it lives elsewhere).

Phase 5 additionally needs `/skill-review` on the `git-state-safety` edit, and Phase 4 needs `plugin-semver`.

## Out of scope

Named residuals, in the style of `docs/design-decisions.md` §44 — each is accepted, not overlooked.

1. **A clean operation stays entirely ungated.** No separate commit call reaches the Bash tool when a merge, rebase, or cherry-pick applies without conflict (G-3), so gate strictness depends on whether a conflict happened. **This residual is not benign, and rows 23/24/28 depend on it not being benign:** it is what makes both admitted anchors' non-dominance leg hold, because forging an anchor for adversarial content is *never* cheaper than this zero-gate path — `commit-tree` a payload, `git branch` it, `git merge` it cleanly, with no separate `git commit` call for any gate to see. For a clean merge of two *already-reviewed* trees this is coherent — nothing novel is authored. For a clean merge of a branch tipped at fabricated, unreviewed content, or for a clean cherry-pick or revert, it is the same severity class as residual 11's `bash -c` bypass: content reaches a commit with literally zero gate. It is strictly narrower than residual 11 only in that it requires that specific clean-apply shape and leaves every conflicted operation gated. It also pre-dates this plan: `_lib_command_invokes_git_subcmd "$COMMAND" commit` never matched `git cherry-pick <sha>` either. Closing it needs a post-tool-call mechanism this design does not have.
2. **Initiating forms are not matched.** `git merge <ref>`, `git cherry-pick <sha>`, and `git revert <sha>` stage nothing at PreToolUse time, so there is no content to hash and gating them would mean gating a prediction.
3. **The trusted-anchor check is ancestry against local refs, and does not fetch.** A merge of a branch that is not reachable from the resolved default remote-tracking ref — a fork branch fetched for inspection, a colleague's branch, a local `main` that is ahead of `origin/main` — over-gates rather than excluding its content. A remote-tracking ref stale enough to have lost the merged commit does the same. Both err toward demanding more review, and no hook performs a network fetch to narrow that. **`origin` naming the shared repository is itself a workflow assumption, not a guarantee** — for a fork-based contributor to this public repo, `origin` is their own fork, so the anchor's soundness leg (row 23) still holds by that contributor's own workflow, but residual 19's stated cost-and-visibility reasoning for the direct-push path does not transfer unchanged; see row 28's fork-topology caveat.
4. **Octopus merges, `cherry-pick -m 2`, and `rebase --rebase-merges` fall back or over-scope.** A multi-line `MERGE_HEAD` falls back; `-m 2` computes against parent 1 and over-reports. A replayed merge commit under `--rebase-merges` would make `REBASE_HEAD^` silently resolve to parent 1 — the one case the OID-validation net cannot catch, since the wrong tree is still a valid tree — but the trust predicate closes it independently, because such a commit reaches neither anchor.
5. **Conflicted files carry conflict markers in the reference blob**, so their novel diff spans marker-text→resolution rather than the resolution alone. Over-scoped, and only within files the reviewer must read anyway.
6. **git below 2.38, or 2.38–2.39 without `--merge-base=`, gets today's behavior.** The over-gating this plan fixes persists there. Unlike `check-branch-divergence.sh:24-27`'s documented old-git degradation, which falsely reports CLEAN, this one fails safe. Both bands are pinned by stub tests rather than left to inference.
7. **`require-plugin-version-bump.sh:90` and `require-npm-version-bump.sh:126` keep the bespoke regex**, and their `hooks.json` entries keep the `"if"` pre-filter the other five drop. Both stay blind to `git -c … commit` and to the `--continue` family, extending SC1's residual, and Phase 3 pins that current behavior with an assertion so the gap is recorded in the suite rather than only in prose. Two reasons for narrowing: the shared matcher's dependency chain would need duplicating into two more trimmed plugin libs with their own parity tests, and arming those gates on `--continue` first requires answering what "version strictly raised since the merge-base" means when the merge itself moved the merge-base (row 7). The duplication cost is recorded in the Phase 5 design-decisions entry, which is this repo's home for tracked residuals.
8. **`deny-invisible-commit-content.sh:144` is deliberately not extended.** Its question is whether a commit carries `-a`, `--`, or a bare pathspec; `git <verb> --continue` accepts none of those and commits exactly the index, so the class it exists to catch cannot arise from those commands.
9. **Content scanners keep the HEAD-relative diff, and newly fire on `--continue` — on all four forms, including rebase.** Narrowing a scanner's input to novel content would let a secret or a private-project reference sitting in already-merged content pass unscanned. The consequence of arming them on `--continue` is that a sync merge importing already-committed content that matches a detector will now deny where today nothing fires. The deny message names the offending file, and the recourse is the same as any other detector hit — there is no mid-merge escape hatch, and this is the deliberate direction for a scanner. **This is a deliberate asymmetry with the rebase carve-out on the two review-marker gates, not an inconsistency in the sweep:** `deny-pii-in-commits.sh` and `deny-private-project-refs.sh` fire on `rebase --continue` exactly as they do on the other three `--continue` forms, while `require-code-review.sh`/`require-skill-review.sh` do not. The two exemption criteria are different by design — the marker gates are exempted because their recourse is a review, which is the expensive thing the carve-out avoids demanding mid-rebase; the scanners are not exempted because their recourse is mechanical (unstage the value), and their threat model is accidental leakage, which does not route around whichever gate happens to be armed.
10. **`docs/reports/2026-08-22-discovery-audit/findings.md` is not edited**, even though SC1's stow-tree line numbers are stale. It is a dated audit record — a preserved-content category, read-only absent a ticket that says otherwise.
11. **`bash -c` / `eval` / git-alias wrapping still bypasses detection** (S13, S14). Unchanged by this plan and unchanged in either direction.
12. **Content-addressed marker semantics are kept, not revisited.** The stored hash *is* the authorization (`docs/hooks.md:89`). Because the no-in-progress-state path issues the identical command it issues today (row 18), no marker on disk invalidates when any phase lands, and no round counter resets — the earlier draft's one-time-invalidation residual dissolves rather than being accepted. Redesigning the scheme to decouple authorization from the preimage would make any future base change a non-event, and is still declined: it would replace a scoped gate fix with a rewrite of the mechanism all five marker kinds depend on.
13. **Mid-operation preimages have no back-compatibility story, and need none.** A marker written mid-merge before a phase lands cannot match after it, but no such marker can be in flight: the states this plan newly gates are states no gate reaches today.
14. **Rebase and unmerged-source cherry-pick over-gate where they're still gated at all, and no third anchor is added.** `REBASE_HEAD` reaches neither admissible anchor in the ordinary case, so for the consumers still armed on `rebase --continue` — `_lib_active_plan_files`, `marker.sh status`, and a bare `git commit` made mid-rebase without `--continue` — the base stays empty and hashing stays HEAD-relative. This no longer means re-reviewing a replayed commit at every conflicted step: the rebase carve-out means `require-code-review.sh` and `require-skill-review.sh` never fire on `git rebase --continue` at all, so the over-gating this residual originally described for those two gates does not arise. What survives here is narrower — the anchor genuinely never resolves for rebase, which matters only for the smaller set of consumers the carve-out leaves reachable. Two candidate third anchors were considered and both are declined against row 23's repaired admissibility test:
    - **`REBASE_HEAD` reachable from `ORIG_HEAD`** — `ORIG_HEAD` is a gitdir file any `printf` writes at zero cost, and nothing removes or contradicts a fabricated value. Fails soundness: reaching it never implied passing review, honestly or otherwise.
    - **`REBASE_HEAD` reachable from any `refs/remotes/*` ref** — proposed in the first revision and withdrawn (row 25). Fails soundness for the same reason as `ORIG_HEAD`: `require-ready-for-review.sh` no-ops with no open PR (`:314-319`), exits early on the default branch (`:293-295`), and fails open when `gh` errors (`:309-318`), so reaching a remote-tracking ref never implied having passed an automated review gate. Recorded here explicitly so a later reviewer meets the reasoning rather than re-proposing the anchor.

    **Reopening criterion is the repaired admissibility test, not accumulated annoyance, and it is not a fixed bar.** A new anchor is admitted only when it passes both legs of row 23 — mid-rebase friction on its own is evidence for neither. Both candidates above fail on soundness, the leg the repair left unchanged, so today's declines stand regardless of the repair. But the non-dominance leg is not fixed either: it depends on residual 1 (the clean-merge zero-gate bypass) and residual 11 (`bash -c`/`eval` wrapping) continuing to exist and continuing to be cheaper than any candidate anchor's forgery cost, so if either bypass is ever closed, this row's declines — and both admitted anchors in row 23 — must be re-run. The residual is stated in terms of what the *agent* can satisfy rather than how many humans use the machine — a single-operator machine is the normal case for this repo and for stow consumers generally, but it does not narrow the threat, because the agent runs under the operator's own credentials either way. *Unscoped forward sketch, not a commitment:* an anchor of the form "`REBASE_HEAD` is an OID for which a code-review marker already exists" would pass the test, since it reduces to the `HEAD` case — satisfying it requires having passed the gate for that content. It does not work today: markers store a staged-diff hash, not the commit OID they authorized, so no such lookup exists. Designing or scoping that is explicitly out of this plan.
15. **Default-branch resolution is duplicated.** `_lib_resolve_default_branch` in `_lib.sh` (row 16, pre-existing — this plan calls it, doesn't add it), `resolve_default_branch` in `pr-diff-against-base.sh:8-22`, and (once this phase lands) a third copy in the plugin lib (G-2). Consolidating the first two would mean sourcing `_lib.sh` into a `set -euo pipefail` script, an interaction no script in this repo currently exercises — `marker.sh` sources it under bare `set -u` — and verifying it is not this plan's job.
16. **The stow and plugin copies of the state-detection helpers remain two maintained implementations.** The standing differential tests over shared fixtures make a divergence fail CI rather than silently wedge the skill-review gate mid-operation, which is a structural guarantee the fixed-input parity shape does not provide — but it is a test-enforced invariant, not a single implementation, and G-2 forecloses the latter.
17. **`merge-tree`'s loose objects accumulate before gc reclaims them, and under `gc.auto=0` nothing reclaims them at all.** They are unreachable from any ref or reflog, but `gc.pruneExpire` defaults to two weeks and `gc.auto` triggers on ~6700 loose objects, so in a default-configured repository cleanup is bounded and eventual rather than prompt. The only backstop is the `git gc --auto` that ordinary git commands already run, and `man git-config` states that setting `gc.auto` to 0 disables not only loose-object packing but every other heuristic `git gc --auto` uses to decide whether there is work to do. Large monorepos commonly set it to 0 precisely because auto-GC is disruptive at their scale — and that is the same repository class where each trial merge writes the most objects and where these hooks fire, since they run in whatever repo the contributor has open rather than in claude-config. There, this plan's writes are never automatically reclaimed and "bounded and modest" does not hold. The plan measures no per-merge or per-session object count, so "modest" describes the default configuration and is not a measurement; nothing here prunes its own writes either. The `_lib_capped` cap bounds the per-invocation *time*, not the object count.
18. **The round-3 architect-consult gate stays disarmed for the duration of a rebase — pre-existing, and this plan does not widen it.** `_lib_reviewer_round_state_key` keys on the branch name and returns empty on a detached HEAD, which is the state a rebase runs in, so both `require-architect-consult.sh:90` and `log-reviewer-round.sh:65` take their allow / no-record path throughout (row 27). The fail-open itself is pre-existing and deliberate — `require-architect-consult.sh:14-17` lists detached HEAD among its documented allow-on-state-failure cases. An earlier draft of this plan gated `git rebase --continue` through `require-code-review.sh`, which would have made this window routinely reachable by compelling a `/code-review` (and reviewer fan-out) mid-rebase where nothing compelled one before; the rebase carve-out withdraws that change, so `require-code-review.sh` never fires on `rebase --continue` and this window's reachability is unchanged from today. **This plan accepts the gap rather than fixing or partially mitigating it — for a smaller reason than an earlier draft gave it.** Phase 2 still touches the adjacent `_lib_reviewer_round_state_value` (its diff-hash half only), so this residual is recorded to stop a reader from assuming that change made the round-state machinery rebase-correct; it does not, and the disarm lives in the key's branch half and the value's head-sha half, neither of which Phase 2 touches. Fixing it means giving that key a rebase-aware branch source — `rebase-merge/head-name`, or the pre-rebase branch — which is a change to §41's gate design with its own fail-direction analysis, not a call-site sweep. Phase 1 asserts the detached-HEAD premise and Phase 2 asserts the disarm, so the residual is pinned in the suite rather than only in prose. Kept separate from residual 13, which is about marker preimages having no in-flight back-compatibility problem and is unrelated.
19. **Content pushed directly to the remote's default branch is trusted by the predicate, and no local hook stops that push.** An agent can build a commit with `git commit-tree` — which `require-code-review.sh` never matches, since that hook keys on `git commit` (G-6) — push it with an explicit refspec to the default branch, and then `git fetch` legitimately. `refs/remotes/origin/<default>` afterwards genuinely holds that content. Row 28 traces exactly why `require-ready-for-review.sh` allows the push: its default-branch bypass, its no-open-PR exit, and its marker check all key on the *checked-out* branch rather than the push destination, and its own header declares a cooperative rather than adversarial threat model (`:94-95`). Accepted rather than closed, under the repaired admissibility test (row 23): the path is dominated by residual 1's cheaper zero-gate bypass, so the anchor grants no leverage that bypass did not already grant — the same shape as row 14's `HEAD` caveat. **This holds regardless of `origin`'s topology, but the reasoning that the push is additionally "loud" (visible to every clone, CI run, and reviewer) does not** — that visibility assumes `origin` is the shared repository, which fails for a fork-based contributor pushing to their own fork's default branch (out of scope #3). The verdict is unaffected, since non-dominance against residual 1 does not depend on loudness, but a future reader should not cite loudness as an independent reason this path is safe for every contributor. Closing this locally would mean a new gate parsing `git push` refspecs and destinations, a redesign of `require-ready-for-review.sh`'s matcher and fail posture rather than a call-site sweep, in a file this plan otherwise does not touch. Server-side branch protection may refuse the push independently, but that is a per-repository GitHub setting these hooks cannot verify and cannot assume — a branch-protection API probe against this repository returned 403 during planning, so the plan claims nothing about it in either direction. Phase 1 assertion 9 pins the local behavior so the gap lives in the suite rather than only here.
20. **`_lib_capped`'s cap is not a universal backstop, and a status-2 fallback is distinguishable from a genuine no-state result only in a deny message.** `_lib_capped_for` (`_lib.sh:38-48`) probes `timeout(1)` then `gtimeout(1)` and runs the wrapped command **uncapped** when neither is on PATH; `install.sh:891-900` warns about that at onboarding and continues. Two distinct consequences follow, and neither is corrected here. Without either binary there is no cap at all, so a `merge-tree` against a large repo stalls the tool call for as long as it takes, governed only by the harness's own hook timeout — the same posture `_lib_jq`'s comment already records for a stalled jq, now extended to a heavier command. With a binary present and a repo large enough to exceed 5s, the cap fires, `_lib_gate_diff_base` returns status 2 with an empty base, and the merger is charged for upstream's content exactly as before this plan — this plan's own bug, reappearing for that contributor. Making `install.sh` fail rather than warn is declined: it would block onboarding on stock macOS without Homebrew coreutils, a change to install policy for every stow consumer that is out of proportion to a gate fix, and it would not help anyway, since nothing re-checks PATH after install. The mitigation taken is narrow and diagnostic rather than corrective — `require-code-review.sh` and `require-skill-review.sh` name the undetermined base in the deny message they were already emitting, so the contributor sees why the wide diff came back instead of concluding the feature does not work. No log file, counter, or telemetry surface is added, and the other consumers (`marker.sh`, `_lib_active_plan_files`, `_lib_staged_length_gate`, `_lib_reviewer_round_state_value`) stay silent on status 2 because none of them is the surface a confused contributor is reading.
21. **The two existing `merge-tree --write-tree` call sites stay unwrapped.** `check-branch-divergence.sh:98` and `branch-divergence-status.sh:64` invoke the primitive with no `_lib_capped` and no timeout of their own — only the `git fetch` preceding them is time-bounded, by a bare `timeout 2` (`check-branch-divergence.sh:80-86`). If `merge-tree` hangs in either script today, nothing stops it. Pre-existing, unrelated to the in-progress states this plan gates, and in two files this plan's Critical files does not name — so it is recorded rather than fixed, and M-1 cites that precedent for the primitive's tree-and-index safety only, never for its latency posture.
22. **The rebase carve-out is command-shaped, not state-shaped, and a bare `git commit` made mid-rebase (not via `--continue`) is unaffected by it.** `_lib_command_concludes_marker_gated_commit` excludes exactly one command shape — `git rebase --continue` — not the whole rebase state. An agent that resolves a rebase conflict and runs a bare `git commit` instead of `git rebase --continue` (a legitimate, if less common, git workflow — the two are not equivalent, but both conclude the current step) still reaches `require-code-review.sh`, still gets the HEAD-relative over-gating residual 14 describes, since `REBASE_HEAD` still reaches no admissible anchor. A state-shaped carve-out — suppress the marker gates whenever `rebase-merge/`/`rebase-apply/` exists, regardless of command — was considered and declined: it would also exempt genuinely novel work an agent stages and commits mid-rebase for reasons unrelated to the replay (e.g., amending an unrelated file before continuing), which is exactly the content this plan's marker gates exist to catch. The carve-out is deliberately narrower than "anything that happens during a rebase."
23. **The command-shape exemption covers more than genuine conflict resolution, and the carve-out's own cost/benefit framing (above) undersells that.** `_lib_command_concludes_marker_gated_commit` is a pure string matcher on `git rebase --continue` with no state or conflict check behind it — confirmed empirically this revision: a trivial, no-conflict interactive rebase marking a commit `edit` (via `GIT_SEQUENCE_EDITOR`, fully agent-controlled, no interactivity and no conflict required) pauses with `rebase-merge/`/`REBASE_HEAD` present exactly as a genuine conflict would; staging an entirely unrelated file at that pause point and running `git rebase --continue` with no separate `git commit` silently folds it into the replayed commit, invisible to `require-code-review.sh`/`require-skill-review.sh`. This is not a new bypass the carve-out creates — `require-code-review.sh` has zero `rebase --continue` awareness today, so the underlying command-shape gap pre-dates this plan — but the carve-out is the point at which the exemption's scope was set, and "conflict-resolution content" describes a narrower exposure than "any staged content at any rebase continuation point, conflict or not." The five non-marker gates still catch a literal secret, PII pattern, private-project reference, oversized file, or session-key change in laundered content; they would not catch an unreviewed logic change to a hook script, a `SKILL.md` edit, a `plugin.json` tamper, or any other change outside those specific mechanical patterns. Cost-wise this path is not obviously more expensive than residual 1's `commit-tree`/`branch`/`merge` plumbing sequence, and is arguably stealthier in a session transcript, since an interactive rebase reads as the routine "clean up my last commit" activity `git-feature-branch-sync/SKILL.md` already prescribes, where residual 1's raw plumbing commands do not. Row 23's admissibility test does not govern this decision — that test selects which *anchors* a gate may trust to exclude content from a hash; this is a decision about whether to gate a *command shape* at all, made on the narrower cost/benefit grounds stated in the carve-out subsection above, now corrected to disclose the true exposed surface rather than the conflict-only framing.
