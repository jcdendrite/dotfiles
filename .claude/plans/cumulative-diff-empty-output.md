# Empty-input classification in the marker hash sites

## Context

Stop classifying a legitimately empty diff as a tool failure, and repair the
sibling emptiness guards that cannot fire. A reviewer working in an unrelated
repo reported a suspected bug in the cumulative-diff review cache: once a
branch's PR merges, `pr-diff-against-base.sh` returns empty stdout, and they
claimed hashing that empty output yields the SHA-256-of-empty-string constant
`e3b0c442…b855` — a value any zero-diff branch would produce identically,
colliding as a marker value. A direct probe disconfirmed that claim for the
cumulative-review arm, which guards its input *before* hashing and is pinned by
`test_write_aborts_when_diff_is_empty`. The investigation confirmed two adjacent
real defects instead: a legitimately empty cumulative diff is reported to the
engineer as a tool failure (so `/ready-for-review` on an already-merged branch
runs a vacuous `/code-review` and then aborts with an error naming three causes
that did not occur), and four sibling sites write the same-shaped guard *after*
the hash, where `sha256sum`'s fixed-width output makes it unfireable. The
intended outcome is one change closing both.

## Approach

Fix the empty cumulative diff at the skill layer, and repair the four sibling emptiness guards by classifying the *result* of the hash itself rather than probing the input beforehand. `/ready-for-review` step 3 gains a halt for an empty `pr-diff-against-base.sh` result, so a merged branch never reaches `marker.sh write cumulative-review`; `marker.sh` and `_lib.sh` keep the cumulative arm's two-outcome contract and only get their two misleading message strings corrected. At the four sibling sites, extend `_hash_staged_diff` — a helper added by a sibling PR (#910, merged to `main` while this plan was in review) that already gates the hash on git's real exit status via a scoped `pipefail`, correctly distinguishing a failed or timed-out git call from a real digest — with a third, distinguished return state for a genuinely empty diff, rather than adding a second, separately-timed probe-based classifier ahead of the same call sites. Each site then does what its own gate already does with that state: abort on unanswerable (return 1, unchanged), decline-without-a-marker on empty (the new distinguished return code), hash unchanged on content (return 0, hash on stdout, unchanged). `_lib_staged_diff_state` — the probe-then-classify helper this plan originally introduced for all five sites — is deleted outright rather than narrowed: `_lib_reviewer_round_state_value`, its one remaining caller, hashes through `_lib_staged_diff_hash` for the no-override path and inlines its own base-relative empty-diff check for the override path, mirroring `_lib_code_review_marker_value`'s own shape, so no probe-then-classify helper remains anywhere in `_lib.sh`. No hashed bytes change anywhere, so no existing marker on any stow consumer's machine is invalidated.

**Root problem.** `sha256sum` turns zero bytes into a full 64-hex digest. A sibling PR (#910, merged to `main` while this plan was in review) closed half of this from a different angle: `_hash_staged_diff` gates the hash on git's own exit status, so a failed or capped git call can no longer masquerade as a valid digest — but it does not distinguish that valid digest from the digest of a genuinely empty diff, so every write-arm call site still writes a marker (and `check` still runs its own separate, hardcoded-at-runtime empty-digest comparison) when nothing is staged. This plan closes the remaining gap by giving `_hash_staged_diff` a third, distinguished return state for the empty case, letting each call site skip writing a marker without a second, separately-timed probe call — and letting `check`'s existing empty-digest comparison collapse into the same mechanism. The one site that does check emptiness first today, `_lib_cumulative_diff_hash`, reports a legitimately empty branch diff as a tool failure — fixed at the skill layer, unaffected by this redesign.

**Givens** (fixed conditions this design accepts, each beyond its own reach):

- **G1 — `sha256sum` emits a 64-hex digest for empty input.** Coreutils behavior; the design must work around it rather than change it. `[verified: probe run this session — empty-string digest `e3b0c442…b855` vs. `_lib_cumulative_diff_hash` returning rc=1 for the same input]`

## Out of scope

- **Not changing `pr-diff-against-base.sh`'s exit contract.** It exits 0 with empty stdout when the merge-base equals HEAD, and exits 1 with a stderr line naming the cause on gh/merge-base failure. It is the shared producer for the write arm and the status arm; changing its exit contract would ripple into both and into `_lib_cumulative_diff_hash`'s cap handling, so this plan leaves it as is. `[verified: claude/.claude/scripts/pr-diff-against-base.sh:5,24-38]`
- **Not changing `require-code-review.sh` / `require-skill-review.sh`'s empty-diff posture.** They already exit 0 on the same empty state a write arm would face today. `require-code-review.sh:93` is documented as one half of a named coupling with `deny-invisible-commit-content.sh` ("do not remove either half independently"), so this plan takes their posture as fixed and matches it rather than changing it. `[verified: claude/.claude/hooks/require-code-review.sh:89-95; plugins/skill-management/hooks/require-skill-review.sh:102-118]`
- **The `unknown`/`empty` split not extending to `require-code-review.sh` / `require-skill-review.sh`'s read-side checks.** After row 10, `marker.sh write code-review` / `write skill-review` fail closed on `unknown` (abort, no marker). `require-code-review.sh:93` and `require-skill-review.sh:116` keep a raw `[ -z "$(git … diff --cached 2>/dev/null)" ]` test that is true both when nothing is staged and when the `git diff` invocation itself fails, so they still conflate "can't tell" with "nothing to review" and fail open on both. This is pre-existing and not worsened by this plan — the read side behaved this way before this change too. It needs naming here because the bullet above ("already exit 0 on the same empty state") stops precisely describing reality for the `unknown` case the moment row 10 ships.
- **Not changing `enforce-marker-script-shape.sh`'s chain allowlist.** It explicitly allows `marker.sh write <skill> && git commit` chains. That allowlist is a separate security gate; rows 10 and 11's exit-code choices at the write arm must stay compatible with a shape the gate blesses, without this plan touching the gate itself. `[verified: claude/.claude/hooks/enforce-marker-script-shape.sh:607,619-628]`
- **Not re-deciding whether an empty staged diff is a legitimate `_lib_reviewer_round_state_value` result.** `test_require_architect_consult.py`'s `_repo_at_cap` deliberately drives a round-2 state with nothing staged, and the round-3 consult gate's counting depends on that value existing; re-deciding it belongs to that gate's own design, not here. `[verified: claude/.claude/hooks/tests/test_require_architect_consult.py:42-56 (per Step 3 evidence); claude/.claude/hooks/_lib.sh:2257-2263]`
- **The 0-byte plan-file sites** (`marker.sh:318`, `marker.sh:545`, `claude/.claude/hooks/require-plan-review.sh:111`). Deliberately excluded, not overlooked: those hash a real file's bytes, so the empty-input digest there is the *correct* content hash of a 0-byte file, and their `[ -z "$PLAN_HASH" ]` guards do fire (a missing or unreadable file makes `sha256sum` print nothing). The only residual is a same-session plan-mode target swapping between two distinct 0-byte plan files — a degenerate state, and a different bug shape from the failed-vs-empty conflation this change closes.
- **`_lib_active_plan_hash`** (`_lib.sh:458-484`) — its `[ -n "$active_files" ] || return 0` short-circuits before any hashing, so it never had the defect.
- **A new `docs/design-decisions.md` entry.** The rule this change establishes ("classify the hash input before hashing; an empty input follows the corresponding gate's own posture") gets exactly one canonical home: `_hash_staged_diff`'s header comment in `marker.sh`, the shared body all four sibling call sites route through and where the next contributor adding a hash site will be. `§44` is a dated decision-log entry recording a decision that this change refines rather than reverses, and CLAUDE.md Axis 3 makes it read-only.
- **`docs/hooks.md:89`.** Its claim — a completion marker's content is "a hash of exactly the state that was reviewed" — stays true after this change and is in fact strengthened by it, so it needs no edit.
- **Converting the two `require-*` hooks to a shared hashing helper.** Both currently recompute the staged-diff hash with their own inline `git diff --cached | sha256sum | awk` pipeline (`require-code-review.sh:108`) rather than sharing one. The right long-term shape is one recipe, one place, but converting changes the hashed bytes, invalidates every marker in the field, and requires a plugin version bump since `require-skill-review.sh` lives inside a versioned plugin. Raise it separately if marker-recipe drift ever actually bites.
- **Pre-pull poisoned entries in `.reviewer-round-state.d`.** Rows 15/17 analyze backward compatibility for completion markers only. A line recorded before this fix ships can hold `<head-sha> <empty-digest>` for a diff that was actually unanswerable, and `require-architect-consult.sh:107`'s `grep -qFx` still matches that line against a later, genuinely empty diff at the same HEAD after the fix ships. With `_LIB_REVIEWER_ROUND_STATE_CAP=2` (`_lib.sh:2229`), a poisoned line can occupy one of only two slots for the remaining life of that branch's ledger; the 30-day sweep (`log-reviewer-round.sh:114`) deletes whole files rather than lines and fires only as a side effect of a write to that same file, so an actively-worked branch keeps refreshing the file's mtime and the poisoned line never ages out. Accepted as a bounded residual: `require-architect-consult.sh` is documented as a cost-and-quality interruption, not a security control, so the effect is a suppressed consult nudge for that branch, not a bypass. Deleting that branch's `.reviewer-round-state.d` file resets it, if a clean slate matters.
- **`clear-stale` coverage for completion markers.** Legacy empty-digest markers become inert under row 14 rather than harmful, so no eviction path is needed here.
- **A no-op `GIT_EXTERNAL_DIFF`/`diff.external` driver making `_hash_staged_diff` misclassify real content as empty.** Confirmed empirically this session (see row 9): such a driver makes the hashed `git diff --cached` call itself produce zero bytes for genuinely staged content, so the write arm exits 0 with no marker instead of reviewing real content. Pre-existing exposure carried over unchanged from the pre-#910 raw hashing pipeline, not introduced or worsened by this design -- the same no-op driver already produced the same wrong digest before this plan. Accepted because fixing it would require reintroducing a `--quiet`-shaped probe ahead of the hash, which is the exact TOCTOU-risk shape this design removes, to detect a driver misconfiguration nobody has reported hitting in practice. Pinned by `TestHashStagedDiff::test_git_external_diff_noop_still_classifies_as_content` (`test_marker_script.py`) so a future change to this behavior is a visible test diff, not a silent regression.
- **Loss of the write arms' incidental fail-fast timeout on a hung `git`.** Before #910 (merged to `main` while this plan was in review), the write arms' probe-then-hash shape happened to cap the probe stage, so a genuinely hung `git diff --cached` (stuck index lock, unresponsive filesystem mount) was caught within that cap and the write arm aborted before ever reaching the deliberately-uncapped hash stage. #910 already removed that probe in favor of the same single uncapped `_hash_staged_diff` call this plan extends, so a hung `git` at the write arms now blocks indefinitely with no cap and no diagnostic — inherited from the shape PR #910 already merged, not introduced by this plan. `[verified: staff-platform-engineer plan-review consult this session — read marker.sh's `write` arms' cap/uncap shape directly]`
